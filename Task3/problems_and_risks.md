# Проблемы и риски взаимодействия сервисов InsureTech

## 1. Проблемы

### 1.1. Синхронная агрегация каталога

Длительность ответа агрегатора определяется самой медленной страховой компанией. Таймаут или ошибка одной компании прерывает весь запрос. Локальная копия в этом случае не обновляется. Такие сбои уже наблюдаются при взаимодействии с API страховых компаний.

### 1.2. Обновление копий по расписанию

Актуальность локальной копии ограничена периодом опроса. Для `core-app` расхождение с источником достигает 15 минут, для `ins-comp-settlement` — 24 часа. Полис может быть оформлен по тарифу, который к моменту формирования реестра взаиморасчётов уже заменён.

### 1.3. Независимое обновление копий

Общий поток изменений каталога отсутствует. `core-app` и `ins-comp-settlement` обновляют копии с разной периодичностью, поэтому копии расходятся и при успешном завершении обоих опросов.

### 1.4. Пакетная передача оформленных полисов

Суточная выборка передаётся одним запросом. Частичный результат не предусмотрен: запрос либо завершается успешно, либо не передаёт данные за сутки. Недоступность `core-app` в ночном окне оставляет `ins-comp-settlement` без реестра. Повторный запуск без идемпотентной обработки приводит к пропуску записей либо к их повторному учёту.

## 2. Риски при увеличении нагрузки

Число страховых компаний увеличивается с пяти до десяти. Каждый дополнительный участник увеличивает длительность синхронного опроса и вероятность того, что хотя бы один внешний API не ответит в установленный срок. Сокращение периода опроса снижает устаревание копий, но линейно увеличивает нагрузку на внешние API: она растёт вместе с числом компаний и частотой запросов.

Рост числа оформлений после рекламной кампании увеличивает объём и длительность ночного запроса всех полисов за день. Допустимое окно выполнения этого запроса не расширяется. Неполный реестр ведёт к ошибке расчёта агентского вознаграждения и к расхождению с данными страховой компании.

Для пользователя последствие выражается в отображении неактуальной цены либо в ошибке оформления в период, когда агрегатор не собрал каталог. Для партнёра B2B то же состояние выглядит как нарушение SLA. Вызов партнёра в `core-app` при этом завершается штатно: деградация связана с фоновым обновлением справочных данных.

## 3. Принятые решения

На схеме контейнеров изменены три внутренние связи. Они переводятся с синхронного REST на поток событий Apache Kafka. Назначение сервисов сохраняется.

| Топик | Издатель | Подписчики | Назначение |
| --- | --- | --- | --- |
| `products.tariffs` | `ins-product-aggregator` | `core-app`, `ins-comp-settlement` | Обновление локальных копий каталога |
| `policies.issued` | `core-app` | `ins-comp-settlement` | Передача оформленных полисов |

Агрегатор опрашивает страховые компании самостоятельно и по отдельности. Ошибка одной компании не отменяет публикацию изменений, полученных от остальных. Опрос каталога по таймеру со стороны `core-app` и `ins-comp-settlement` исключается. `ins-comp-settlement` получает полисы по мере публикации событий, а не одной суточной выборкой.

Синхронными сохраняются взаимодействия, в которых требуется немедленный ответ либо контрагент является внешней системой:

- обращения сайта и партнёров к `core-app`;
- проведение оплаты;
- обмен с `client-info`;
- вызовы API страховых компаний;
- ежемесячная передача реестра взаиморасчётов в страховые компании.

### 4. Transactional Outbox

Паттерн Transactional Outbox применяется на обоих издателях. Запись бизнес-данных и запись события выполняются в одной транзакции локальной базы. Публикацию в Kafka выполняет отдельный процесс, читающий таблицу outbox. Тем самым исключаются два несогласованных исхода: сохранённый полис без события и опубликованное событие при откате транзакции записи полиса.

- В `core-db` одной транзакцией сохраняются полис и строка outbox. Публикатор отправляет событие в `policies.issued`.
- Для агрегатора вводится база `aggregator-db`. Снимок каталога и строка outbox фиксируются одной транзакцией. Ранее у агрегатора не было хранилища, в котором можно было атомарно отметить факт получения тарифа до его публикации.

Подписчики обрабатывают события идемпотентно. Повторная доставка не создаёт второй полис и не применяет изменение тарифа дважды. Локальные копии каталога сохраняются; периодический опрос как способ их обновления не используется.
